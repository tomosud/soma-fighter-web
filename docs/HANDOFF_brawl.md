## 3. 構成（どこに何があるか）

| ファイル | 役割 |
|---|---|
| `fight.html` | ページ。開始ボタン（`#go`）、英語の操作説明（`#help`）、HP バー |
| `src/fight.js`（約 3100 行） | ゲームのすべて：打撃の選択、反応、AI、層、カメラ、描画、入力 |
| `src/motion.js` | `Track`（生成フレームの再生・つなぎ）と `Scheduler`（要求をまとめて 4 人分を 1 回で推論。1 フレーム 3 ms までずつ組み立てる） |
| `src/soma.js` | 骨格・FK・MotionBricks の入力エンコードと出力デコード（`pose.rot` は**ワールド回転**） |
| `src/posedb.js` | モーションマッチング用の参考ポーズ DB と探索（16 件の箱で枝刈り） |
| `src/ragdoll.js` | 能動ラグドール（XPBD 粒子、筋肉、床、摩擦、`gravity` / `friction` / `dampScale`） |
| `src/playlog.js` | プレイ記録（`eval_out/play_<日時>_pNN_log.json`、`perf` イベントは 1 秒ごと） |
| `src/autoplay.js` | ボットのシリーズ（skilled / novice / person）と採点帯 |
| `tools/swing_bench.js` | ベンチ：打撃の振り幅、ポップ、生成待ち、**足の滑り（状態別）**、シリーズの点 |
| `tools/serve.mjs` | ローカルサーバ（ログの追記保存 `/append-log/`） |
| `assets/fightdb.*` | 打撃・反応・倒れ・起き上がりのクリップ 506 本（Mixamo 由来） |

### 1 体ぶんの表示ができるまで（毎ステップ、60 Hz 固定）

1. `scheduler.tick`：要求を組み立てて GPU（WebGPU、1 回 0.13〜0.23 s）へ送る。
2. `Track.advance`：生成フレームを再生する。
3. 表示用のポーズ `F.shown = clonePose(F.track.display)` に、次の**層**を順に重ねる：
   - `ragStep`（ラグドール。KO なら全部ラグドール）
   - `knockOn`（反応が来るまで一撃の向きへ運ぶ）
   - `balanceLayer`
   - `hitPush`（当たった部位をはじく）
   - `breathe`
   - `footLock`（着地した足を留める）
   - `leadLayer`（入力に先行して腰と胴が前に出る。足は残す）
   - `anticipate`（押した瞬間の予備動作）
   - `specStrike`（押した直後から上半身を打撃の頂点へ寄せる）
   - `jumpLayer`（ジャンプキック）
   - `settleLayer`（打った後の行き過ぎと沈み込み）
   - `setOffLean`（歩き出しの傾き）
   - `aliveLayer`（止まっているときの微小な動き）
   - `homing`（拳・足を的へ寄せる IK）
4. ほかに、トラック自体を動かす処理がある：
   - `shove` / `shoveOn`：受けた一撃で体を押し出す。
   - `slideOn`。
   - `trackIn`：敵の打撃が相手を追う（30 cm まで）。
   - 体どうしの押し合い。
   - 生成の要求そのものに入る加工：
     - `windPose` / `chamber`：振りかぶりの姿勢を文脈として渡す。
     - `bigTop`：頂点を誇張する。
     - `reachLimb`：手足を的へ IK で寄せる。
     - `warpStrike`：Mixamo から測った緩急で再生速度を変える。
5. 描画は直近 2 ステップの間を補間する（`F.R`）。

## 5. 効いたこと・効かなかったこと

**効いた（残すべき）**
- 描画の補間（120 Hz 画面でのジッター解消）。
- 要求の組み立てを複数フレームに分けること。
- 探索を箱で枝刈りし、型付き配列で偏りを渡すこと（処理落ち解消。フレームあたり平均 0.5 ms 前後）。
- 敵が行き先を予測して打つこと（`playerAhead`）。敵の命中率が上がった。
- フリックでだけ外れる追尾。
- 速さで硬くなるばね（ω 3.7→8.6、ζ 0.35→0.7）と、カーソル速度の直結（35%）。
- 開始ボタン、チュートリアル（敵 1 人から）、英語の 1 行説明。
- KO 後のラグドール（崩れ落ちて転がり、摩擦で止まる）。

**効かなかった・裏目に出た**
- **生成された動きをずらして速く見せる**（`track.shift` で投機的に先行させる）→ 足が滑る。70 点まで下がった。**二度とやらない**。
- 層を足していくやり方：
  - 先行・頂点への寄せ・行き過ぎ・ジャンプ・微小な動き・呼吸・はじきなどが同じ関節を別々に回している。
  - 順番や重みの相互作用で、ポーズが不自然になる（65 点）。
  - どの層がどの不自然さを生んでいるかは、まだ測っていない。
- ボットの点数を目標にしすぎたこと。点数帯がユーザーの最新の好みとずれていても、点数は下がるだけで気づけない。

## 6. 残っている問題（優先順の案）

1. **ポーズの不自然さ**（65 点の主因）。何が不自然かはまだ具体的に聞けていない。まずユーザーに具体例を聞くか、録画で探す。
2. **押しても打撃が出ないことがある**（表示された割合が 46%）。
   - 最新の記録の `presses[].outcome` では、213 回中 187 回が `started`、21 回が `chained` だった。押した入力自体はほぼ受け付けられている。
   - それでも `tStrike`（打撃が実際に表示された時刻）が付いたのは半分だけ。受け付けてから生成された打撃が差し込まれるまでの間に失われている可能性が高い。
     - 候補：別の要求に上書きされた、被弾で割り込まれた、`strikeReq` で技が見つからず移動に落ちた、ログの `pressId` の対応漏れ。
   - まずここを調べる価値が高い（遅さの体感にも直結する）。
3. 腰の追従の遅れ（0.8 s、最新のユーザー記録）。滑らせない範囲では、生成の速さ（遅延 0.13〜0.23 s ＋ 文脈のずれ）が下限になる。
4. ボットの採点帯を、今の方針（敵は当ててくる、かわすのが腕）に合わせて直す。

## 7. 新しい視点の提案（次のセッションへ）

- **層を減らす方向で考え直す**：
  - 「生成された動き」と「物理（ラグドール）」の 2 つを主役にし、手続き的な層は最小限にする。
  - 各層を `tune` で 1 つずつ切り、ユーザーかレビュー役のエージェントに見比べてもらう。不自然さに効いている層を特定する。
  - 層で足していた意図（予備動作、頂点の誇張、重さ）は、なるべく**生成への目標ポーズと文脈**（MotionBricks に渡すもの）に入れる。そうすれば、モデル自身が自然につないでくれる。
- **自然さを数値で測る**（今は測っていない）：
  - 表示されたポーズと、参考 DB（Mixamo 37,000 件）の中で一番近いポーズとの距離。人が取らない姿勢ほど大きくなる。
  - 関節の角速度・角加速度の急変（ジャーク）。
  - 重心が支持基底（足の範囲）から外れている時間（倒れていないのに外れているのは不自然）。
  - 関節の可動域の超過。
  - 手足と体のめり込み。
  - これらを層ごとに切り替えて比べる。
- **見た目の評価をしっかり回す**：
  - 低解像度の静止画ではなく、連続フレームを GIF か並べた画像にして、層を切った版と比べる。
  - 判定役には「人として自然か」を、具体的な関節と時刻で答えさせる。
- **ユーザーと早めに具体を詰める**：どの場面のどのポーズが不自然か（打撃の頂点、被弾、歩き、振りかぶりなど）を最初に聞く。
